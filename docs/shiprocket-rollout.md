# Shiprocket rollout

Shiprocket support is disabled unless `SHIPROCKET_ENABLED=true`. The admin flow is manual: an authorized admin separately confirms provider order creation, courier/AWB assignment, pickup request, and label generation. No checkout or Razorpay handler calls Shiprocket.

## Manual setup

1. The owner reports that migration `20261024120000_shiprocket_shipping.sql` has already been applied and verified in production, including all six columns and two indexes. Do not rerun it there. For a new environment, confirm the Supabase project and database using that environment's Supabase Dashboard before doing anything; inspect its migration history and `public.orders` schema, then run the migration file once in that project's SQL Editor only if it is absent. Verify the six named columns and two indexes after execution. Never select a different project based on a local `.env.local` guess, and do not run this through the application or build.
2. Configure server-only `SHIPROCKET_EMAIL`, `SHIPROCKET_PASSWORD`, `SHIPROCKET_PICKUP_LOCATION`, and accurate package weight/length/breadth/height in kg/cm. Parcel data is not in the current product schema; shipment creation is rejected until all four measurements are set. Verify the pickup location already exists in Shiprocket.
3. Keep `SHIPROCKET_ENABLED=false` until the database migration, pickup location, package configuration, and credentials have been verified. The safe auth diagnostic calls only Shiprocket's authentication endpoint. Shiprocket warns that valid shipping API calls affect real-time account data.
4. Enable the feature only for a deliberate rollout. The admin has separate confirmed actions to create a provider order, assign a courier/AWB, request a pickup, and generate a label. Creating an order and assigning an AWB can alter the live Shiprocket account; pickup can trigger real fulfillment. No such operation is appropriate as a credential smoke test.

## Current API coverage and limitation

The server client uses Shiprocket's documented login endpoint, bearer token validity (ten days), custom order endpoint, AWB assignment endpoint, pickup request endpoint, and label endpoint. Credentials and tokens are never returned to the browser. Admin actions are separate: create the provider order, assign courier/AWB, request pickup, then generate a label. Each lifecycle action uses a durable database reservation. The service locks the order row in a short PostgreSQL transaction, checks current confirmation/status/payment/cancellation/refund fields and lifecycle state, and changes the state to the action's in-progress value before committing. It makes the provider request only after the transaction closes. Cancellation requests/approval, admin status changes, and application refund reservation take the same order-row lock and reject eligibility-changing actions while a lifecycle operation is in progress or unresolved. If cancellation wins first, the shipment claim sees the changed state and fails closed; if shipment claim wins first, those app transitions see the durable reservation and fail closed. This is a cross-instance PostgreSQL row-lock/conditional-state guarantee, not an in-process mutex.

Application cancellation/status changes, application refund reservation/reconciliation, Shiprocket claims, and the Razorpay refund webhook now serialize through the order row. The common lock order is order first, then refund records or webhook inbox rows. The webhook resolves the candidate order, locks and re-reads it, and then stores/applies the minimal signed-event-derived inbox entry in the same short transaction. If shipment state is active or unresolved, it records the provider refund as a pending `refund_records` entry and marks the inbox event `deferred`; shipping claims reject pending or processed refund records. It acknowledges the webhook only after the event and pending refund are durably retained. Once the shipment has been reconciled, an authorized admin can inspect received, deferred, or quarantined events with `GET /api/admin/refunds/webhook-events` and retry a retryable event with `POST /api/admin/refunds/webhook-events` and `{ "eventKey": "..." }`. The retry rechecks the order under lock and applies the saved provider outcome idempotently. SQL serialization/deadlock errors are retried up to three transaction attempts. If storage/processing transaction rolls back or retry exhaustion occurs, the route returns an error; no success acknowledgement was sent, so an operator must monitor Razorpay delivery status and redeliver from its dashboard if automatic delivery does not resume. Duplicate delivery uses a deterministic key derived from event type, provider refund ID, and provider status. Conflicting details for the same key are quarantined for investigation and require manual review. The same pending refund is also available through existing manual refund reconciliation.

The inbox migration `20261024130000_razorpay_refund_webhook_inbox.sql` is new and has not been applied by this work. Production and any deployment used for a pilot must first have this additive migration reviewed and applied through the approved database procedure, then verify the table/index. Until then, this code path will fail closed with a server error and provider redelivery; **the production pilot remains blocked**. A valid provider refund is never discarded just because shipment state is unresolved. Never hold the database transaction or order lock across a Shiprocket or Razorpay network request. Unknown/ambiguous shipment states require operator reconciliation before deferred refund retry.

Label outcomes are distinct: a definitive provider rejection (a clear non-ambiguous client rejection) restores the prior eligible state and may be retried only after an operator reviews the rejection and confirms the cause is corrected. A successful response is persisted as `label_ready`; use the stored label and do not generate it again. A timeout, ambiguous/server error, incomplete response, or local persistence failure becomes `label_unknown` (or remains a blocked in-progress state if persistence itself is unavailable) and must not be retried automatically. Reconcile provider evidence first. Order creation timeouts are stored as `unknown`; AWB and pickup ambiguous results likewise block blind retries. Reconcile the provider state manually before any reviewed local state correction.

Shiprocket's official API reference documents tracking lookup by AWB (`GET /v1/external/courier/track/awb/{awb_code}`) and shipment ID (`GET /v1/external/courier/track/shipment/{shipment_id}`), and lists shipment status codes. The accessible official reference does not publish a response schema or an event timestamp/order guarantee. No tracking refresh is implemented: consuming an assumed response shape or deriving safe status ordering would risk corrupting customer tracking or regressing order state. Existing customer tracking continues to use the existing order tracking fields. Do not map provider shipment states directly onto `orders.order_status`; that application field participates in cancellation, refund, and notification rules.

The official webhook documentation permits an optional security token but does not specify the request header/body location, signing algorithm, or replay protection behavior. No webhook handler is enabled. Confirm the exact authentication contract with Shiprocket before implementing one.

## Verification and test coverage

Lifecycle runtime tests use deterministic mocked database and provider behavior. Refund inbox unit/source tests cover idempotent event keys and durable deferral paths. These mocks do not prove PostgreSQL row-lock interleavings. A real PostgreSQL integration suite must be run against an explicitly approved isolated test database before claiming database-level concurrency validation. No live Shiprocket lifecycle operation is used.

Validation on 2026-10-24: `npm run test` passed, including 28 Shiprocket lifecycle tests and static migration/inbox assertions; `npx tsc --noEmit`, `npm run build`, targeted ESLint, `npx prisma validate` (with a dummy local URL only; no database connection), and `git diff --check` passed. No tests used real PostgreSQL. A real isolated PostgreSQL concurrency test could not run because `TEST_DATABASE_URL`, explicit non-production approval, and ready-schema flags are not configured. Do not substitute `.env.local`. No Shiprocket lifecycle endpoint or Razorpay refund API was called. The new inbox migration has not been applied anywhere by this work.

Mocked lifecycle tests do not replace PostgreSQL concurrency validation or operator verification. Shiprocket tracking refresh and Shiprocket webhook synchronization remain unimplemented; no tests imply these features are ready.

## Ambiguous operation recovery

The service marks uncertain order creation as `unknown`, in-flight creation as `creating`, uncertain AWB assignment as `awb_unknown`, uncertain pickup as `pickup_unknown`, and uncertain label generation as `label_unknown`. Corresponding in-progress states are `creating`, `assigning_awb`, `pickup_requesting`, and `generating_label`. These states block blind repeats. There is no automatic reconciliation endpoint in this application.

For any state in `creating`, `unknown`, `assigning_awb`, `awb_unknown`, `pickup_requesting`, `pickup_unknown`, `generating_label`, or `label_unknown`, do not retry the action. The admin order page keeps the state and recovery callout visible when the feature flag is off. An authorized operator should locate the order in the Shiprocket panel using the exact RIGHTNOWLIFE order reference and inspect provider order/shipment IDs, AWB, courier, label, and pickup state. Compare recipient/order details against the local order before changing local state. If the provider action exists, or its outcome cannot be established, leave the state blocked and have an engineer reconcile recorded provider identifiers and existing order fields through a reviewed, conditional database update. If the operator confirms the provider did not accept the action, an engineer may reset only that operation's state after recording evidence. Do not clear IDs or tracking fields, create a replacement provider order, regenerate an ambiguous label, or request another pickup as a recovery shortcut. Record the Shiprocket reference, verification evidence, operator, and time in the incident/audit record. Disabling `SHIPROCKET_ENABLED` is containment only; it does not cancel or reverse provider-side actions.

## Preflight and single-order pilot procedure

Preflight is an operator checklist, not a dry-run API mode. None of these checks creates a provider order. The auth diagnostic only authenticates; it does not validate shipment eligibility or pickup location existence.

1. **Environment and database:** Confirm the intended production project and the owner-verified applied migration; do not run a migration. During preparation, verify `SHIPROCKET_ENABLED=false`, server-only credentials are configured, and the pickup location and all four parcel measurements are present, finite, and positive. Do not print environment values or tokens. Run `npm run shiprocket:auth-check`; success proves authentication only. Keep the result sanitized.
2. **Pickup and parcel:** In Shiprocket, verify the exact configured pickup location exists and is active. Compare configured weight in kg and length/breadth/height in cm with the packed parcel measured for this order. Configuration being present does not prove the pickup location or measurements are correct.
3. **Order eligibility:** On the admin order detail page, identify one approved order by its RIGHTNOWLIFE order reference. Verify it is confirmed; for prepaid, verify `payment_status=paid`; for COD, confirm COD payment method and server-allowed status (pending payment or paid). Do not pilot partially paid/advance, failed, cancelled, refunded, refund-pending, delivered, shipped, or terminal orders. Confirm state is `not_created`, no provider order/shipment IDs exist, and no tracking/AWB is present. Stop on discrepancies or any unknown/in-progress state.
4. **Recipient and contents:** Compare the order page's recipient name, full delivery address, city/state/postcode, country, and phone with the approved order record. Confirm email is present, postcode has six digits, phone has 10–12 digits, and each line item has a product name, SKU, positive integer quantity, and valid price. Confirm subtotal/discount/shipping values and actual packed parcel measurements. Correct source order data through the normal audited workflow before proceeding; never work around validation in a request.
5. **Approval record:** Record exact order reference, approver, operator, date/time, recipient/parcel verification, pickup readiness, and approval for this single pilot. Keep the operator present for every action. Stop if approval is absent or unclear.
6. **Explicit activation:** Only after steps 1–5 pass, enable `SHIPROCKET_ENABLED=true` through a separately approved server environment change. This audit does not enable it. Open the selected order detail page and verify its identity and recipient again before acting. The UI confirmation names the order and describes the action; confirm only the action currently approved.
7. **Action effects:** **Create Shiprocket Order** creates a real provider order and shipment record in the live Shiprocket account; it does not assign a courier/AWB or schedule pickup. **Assign Courier & AWB** makes a live courier/AWB assignment to that shipment. **Request Pickup (Live)** sends a live pickup request that can schedule an actual courier visit and start fulfillment; do this only when the operator and warehouse are ready to hand over the parcel. **Generate Label** calls Shiprocket to generate and save a label; it does not itself create the provider order or request a pickup. The service allows one label generation, then serves the saved label; an ambiguous result must be reconciled, not regenerated. Check provider billing/terms before any live action; no dry-run mode exists.
8. **Verify after each action before continuing:** In Shiprocket, locate the same order and compare order/shipment IDs, recipient, contents, AWB/courier, label, and pickup state as applicable. Refresh the admin page and compare local state/IDs/AWB. Record evidence and timestamp. Do not proceed until both systems agree. Request pickup only after the operator and warehouse explicitly confirm readiness.
9. **Failure, rollback, and recovery:** On an error, timeout, `*_unknown`, stale in-progress state, or mismatch, stop actions immediately. Set `SHIPROCKET_ENABLED=false` through the approved environment control as containment, then inspect provider state in Shiprocket. This flag does not reverse or cancel provider actions already accepted. Do not retry, clear local IDs/tracking, or create replacement orders, pickups, or labels. Record provider evidence and contact an engineer for reviewed conditional local reconciliation. If an accepted provider action needs cancellation/correction, the authorized operator must use Shiprocket's supported operational process and record its result; a local flag or database edit does not reverse it.
10. **Closeout:** After the one-order pilot is verified, disable the flag and record final local/provider states and evidence. Keep webhook and automatic tracking sync off until Shiprocket documents a verifiable webhook contract or tracking response schema/event ordering needed for safe processing.

## Razorpay refund inbox coordination

Migration `20261024140000_razorpay_refund_inbox_identity_audit.sql` is a separate additive migration for existing inbox installations. It adds the nullable Razorpay source event identifier and payload hash, unique source-event deduplication, per-attempt outcome timestamps, and a database trigger that prevents transitions out of `processed` or `quarantined`. It has not been applied as part of local tests. Before deploying code that requires these fields, an authorized operator must verify the intended database and migration history and separately approve the migration there.

Refund webhooks authenticate the raw request body before parsing it. A valid `x-razorpay-event-id` header is recorded when present; otherwise the code derives identity from a canonical hash of the parsed event payload and stores only the hash. A duplicate source event with a changed payload is quarantined. Each received event, duplicate, processing result, and blocked terminal retry gets a compact inbox-attempt record containing a fixed outcome/reason and database timestamp; raw payload, signature, credentials, and customer details are not written to that audit table. Refund processing remains transactional and idempotent on the refund record key.

PostgreSQL integration tests connect only when `TEST_DATABASE_URL`, `TEST_DATABASE_IS_NON_PRODUCTION=1`, and `TEST_DATABASE_SCHEMA_READY=1` are all present, and the URL points to a loopback PostgreSQL host whose database name contains a standalone `test` or `testing` token and no production-like token. The test suite does not provision a database or apply migrations automatically. The current workspace had no approved test database configured, so concurrency behavior still requires validation on a separately approved isolated PostgreSQL database.
